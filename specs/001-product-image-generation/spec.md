# Feature Specification: 多参考资料电商产品图生成

**Feature Branch**: `dev`

**Created**: 2026-10-31

**Status**: 需求已澄清 — 技术方案和验收待实施验证

**Input**: 运营人员提交两类参考图片和自然语言要求，先审核形态组合图，再生成并审核六视图包装 mock 组合图。

## Clarifications

### Session 2026-10-31

- Q: 人工审核候选图时，哪些偏差应当使图片不能被接受？ → A: 品牌标识、包装文字及已确认的关键结构必须正确；其他视觉差异由业务人员裁量。
- Q: 首版生成任务是否必须设置费用和耗时的硬性上限？ → A: 不强制硬上限；执行前提供可获得的费用与耗时信息，由运营人员决定是否继续。
- Q: 首版遇到技术故障或图片质量不满意时，应如何处理重试和修订？ → A: 原决定为技术故障不自动重试；该部分已由下方最新决定替代。质量不满意仍由运营人员明确请求修订后再生成。
- Q: 首版应接受哪些格式的参考图片？ → A: 支持 JPEG、PNG；文件大小上限后续确定。
- Q: 首版由谁记录候选图片的最终审核结果？ → A: MCP Server 返回候选图供审核；审核及结果记录由外部业务流程负责。
- Q: 生成任务结果不明且无法查询原任务状态时如何恢复？ → A: 停止自动执行并保留结果不明状态，向调用方说明原任务可能仍在执行以及重复费用或产物风险；不得自动标记失败或取消。运营人员了解风险并给予新的明确授权后可发起新尝试，新尝试须关联原任务且不得覆盖原任务真实状态。上游明确失败时报告失败；不自动重试的旧决定已由下方最新技术故障策略替代。结果不明但可查询时优先查询原任务，不重新提交。

- Q: 首版如何设置图片大小和资源保护？ → A: 不设固定业务文件大小上限；仍须校验真实内容、路径、解码资源及可用资源不足时的安全处理，技术保护和上游限制待验证，不以 10 MiB 候选值冒充已批准上限。
- Q: 技术故障的重试及切换策略是什么？ → A: 仅在确认安全且授权覆盖时，每逻辑操作每模型与接口组合最多 3 次（含首次）；默认绘图模型耗尽后可切换已确认的备选绘图模型，两个模型均失败后停止，不额外切换绘图接口。结果不明不得重提。
- Q: 技术故障重试与人工修订如何计数？ → A: 每个逻辑生成操作内，每个模型与接口组合最多 3 次（含首次），仅用于限制技术故障重试；重启或更换 attempt ID 不重置该操作的计数。运营人员主动发起的形态或包装修订不限制修订轮数；每轮是关联历史的新操作，其技术故障重试独立计数，并遵循业务授权和结果不明恢复规则。
- Q: 包装 mock 之前如何确认产品形态？ → A: 一次图像生成产生一张同时包含六种固定视图的形态组合候选图，每个视图左上角标注对应大写英文字母；Host Agent 构造提示词，绘图模型完成画面和标识，无须另外合成。运营人员可多轮提出修订，明确确认具体版本后才能进行包装 mock。每轮生成及修订遵循现有授权和结果不明恢复规则。
- Q: 提示词与授权如何分工？ → A: 受控 Windows 本机单用户模式下，Host Agent 按运营要求构造和修订提示词；Server 接收并绑定实际提示词、任务和参考资料，不另调用 LLM。Host 管理权限并核对本次任务及费用范围；Server 独立可验证性与各 Host 行为待实测，不能将模型自述、布尔值或 API Key 当授权证据。
- Q: 首版支持哪些 Host？ → A: Codex、Claude Code 和 DeepSeek Harness 均属于首版业务范围；各 Host 的实际 MCP 工具调用和授权联调须分别验证，需求范围明确不等于联调已通过。
- Q: 形态候选生成阶段使用哪些参考图？ → A: 仅使用一至六张产品形态参考图，不输入包装设计图；形态修订同样遵守该图片输入范围。整体任务仍需包装设计图供后续 mock 使用。
- Q: 形态组合图如何标识视图？ → A: F=正视、L=左侧视、R=右侧视、B=后视、T=俯视、Q=右上 45° 正交。此映射为项目确认的约定，不宣称所有行业均使用此表。
- Q: 生成包装 mock 时如何使用形态中间结果？ → A: 只上传运营人员明确接受、无需再修订的六视图组合图原文件一张和一至两张包装设计图，单次最多三张；不拆分组合图，也不上传原始形态参考图。原始形态参考仍用于形态阶段，任务输入数量范围不变。
- Q: 首版最终交付什么？ → A: 此前逐张生成并确认六张包装 mock 的决定已由 2026-11-03 变更取代。

### Session 2026-11-03

- Q: 包装 Mock 如何交付与审核？ → A: 形态组合图确认后，一次正常绘图任务生成一张包含 F/L/R/B/T/Q 六视图的包装 Mock 组合图，再由运营人员审核；不满意可明确请求修订，历史版本保留。此决定取代逐张生成和确认六张 Mock 的要求。两个阶段正常各产生一张组合图，修订历史不计入该数量。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 确认形态并获得六视图包装 Mock 组合图 (Priority: P1)

运营人员提交包装设计和产品形态参考资料及自然语言要求，审核并修订形态组合图；确认后生成一张六视图包装 Mock 组合图，由运营人员审核并可请求修订。

**Why this priority**: 这是核心业务结果，包装视觉与产品形态须各有独立来源。

**Independent Test**: 检查两阶段各一次正常生成返回一张六视图组合图；形态版本须经人工确认后才能生成 Mock，Mock 由人工审核，不满意可明确请求修订并保留历史版本。

**Acceptance Scenarios**:

1. **Given** 一至两张有效包装设计图、一至六张有效形态图和自然语言要求，**When** 运营人员授权并确认形态组合版本，**Then** 一次正常包装绘图生成一张六视图 Mock 组合图并交人工裁决。
2. **Given** 任一类别没有有效图片，**When** 运营人员提交任务，**Then** 系统指出缺失类别且不执行生成。
3. **Given** 形态图带有竞品商标或包装图案，**When** 准备目标商品视觉内容，**Then** 这些竞品内容不作为目标品牌视觉来源。
4. **Given** 形态候选图尚未获运营人员确认，**When** 准备包装 mock，**Then** 系统停止并等待确认；运营人员可多次提出修订，明确确认具体版本后方可继续。
5. **Given** 形态候选图已获确认且无需再修订，**When** 执行包装 mock，**Then** 系统只使用该组合图原文件及一至两张包装设计图，单次最多三张，不上传原始形态参考图，并保留两阶段产物的关联。
6. **Given** 运营人员授权形态生成，**When** 绘图模型成功返回形态候选，**Then** 一张组合图中应包含全部六个固定视图，每个视图左上角应有对应大写英文字母标识，由人工审核其内容和大写英文字母标识是否正确。
7. **Given** 包装 Mock 组合图尚未确认或运营人员不满意，**When** 运营人员审核，**Then** 不得标记已批准；可明确请求多轮修订，每轮产生关联的新版本并保留历史。
8. **Given** 一至六张有效形态参考图和任务中的包装设计图，**When** 生成或修订形态候选，**Then** 该阶段仅输入形态参考图，不输入包装设计图，单次参考图最多六张。

### User Story 2 - 使用多视角与补充说明 (Priority: P1)

运营人员提供包装不同区域设计图和多个产品形态视角，并可用自然语言解释用途或重要性。

**Why this priority**: 多张资料能提供互补信息，避免把不同区域或视角当成同一平面。

**Independent Test**: 分别提供正面、背面设计图与多个形态视角，核对资料分类、说明和可报告的不确定性。

**Acceptance Scenarios**:

1. **Given** 同一包装不同区域的设计图，**When** 处理资料，**Then** 系统保留各资料的区域差异，不默认它们描绘同一平面。
2. **Given** 多个不同视角的形态图与自然语言说明，**When** 处理资料，**Then** 系统综合可用的互补形态信息，并考虑说明中的视角、用途或重要性。
3. **Given** 只有单张形态图且背面不可见，**When** 报告结果，**Then** 不得将缺失的背面结构声称为已真实还原。
4. **Given** 某张图片未说明是包装设计图还是形态参考图，**When** 运营人员提交任务，**Then** 系统要求补充该图片的用途，不执行生成；不强制逐张标记视角。

### User Story 3 - 处理冲突、成本和失败 (Priority: P1)

运营人员需要知道参考资料中的明显冲突或关键结构的不确定性，并掌握执行授权及任务结果。

**Why this priority**: 避免混用包装版本、误报还原结果或重复产生费用。

**Independent Test**: 使用相互矛盾的资料和模拟失败任务，核对反馈、授权和重试行为。

**Acceptance Scenarios**:

1. **Given** 包装设计资料存在明显版本矛盾，**When** 准备生成，**Then** 系统报告冲突，不得擅自混用不同版本。
2. **Given** 形态资料在关键结构上明显矛盾，**When** 处理资料，**Then** 系统暂停并请求运营人员澄清；运营人员明确接受不确定性后，可在标明不确定性后继续生成预览。
3. **Given** 确认可重试的技术故障且授权覆盖后续尝试，**When** 执行恢复，**Then** 每个模型与接口组合最多尝试三次（含首次），按 FR-013 的顺序切换；结果不明时先核查原任务状态，不盲目重复提交或切换。
4. **Given** 运营人员对候选图质量不满意，**When** 其明确请求修订，**Then** 可按新的请求及授权生成；不得因质量不满意自动重新生成。
5. **Given** 包装设计存在多个版本，**When** 确定有效版本，**Then** 系统询问运营人员，并以其确认为准，不擅自混用版本。
6. **Given** 系统建议只使用部分参考图以控制成本或耗时，**When** 运营人员尚未确认建议，**Then** 系统不得按该建议筛选执行；经确认后方可使用所确认的集合。
7. **Given** 图片超过已声明的文件大小限制，**When** 运营人员提交任务，**Then** 系统在收费生成前拒绝请求并指出违规图片。
8. **Given** 当前任务与历史任务均有结果，**When** 获取当前任务结果，**Then** 候选图须可追溯至所属任务，不得将历史产物当作当前结果。
9. **Given** 任务成功、明确失败或结果不明，**When** 返回状态，**Then** 系统分别标明对应状态；结果不明时不报告成功或明确失败。
10. **Given** 上游结果不明且无法查询原任务状态，**When** 系统处理该任务，**Then** 停止自动执行、保留结果不明状态，告知调用方任务可能仍在执行及重复费用或产物风险，不自动标记失败或取消，也不未经新授权重新提交。
11. **Given** 上述无法查询的原任务仍结果不明，**When** 运营人员了解风险并明确授权新尝试，**Then** 可发起新尝试并与原任务建立可追溯关联，不覆盖原任务真实状态。

### Edge Cases

- 文件无效、不可访问或类别为空时应识别受影响输入并停止生成。
- 不同参考图的信息量、视角与可信度不同；缺失或不可判定的信息不能当作确定事实。
- 包装不同区域与包装不同版本不可混为一谈；明显版本冲突须报告。
- 包装设计图超过两张或形态参考图超过六张时，系统指出对应类别数量超限且不执行生成；仅接受有效 JPEG、PNG 图片。图片超过已声明大小限制时，须在收费生成前拒绝并指出违规图片。
- 授权不足、上游失败、任务超时或结果不明时，不能报告生成成功或无限重试。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须按包装设计参考资料与产品形态参考资料两个类别接收图片集合；首版包装设计图为一至两张，形态参考图为一至六张，每张均须有效。
- **FR-002**: 系统必须允许每类包含多张图片；不得将输入硬编码为恰好两张或将形态参考限定为单张。
- **FR-003**: 系统必须接收运营人员的自然语言生成要求；运营人员必须逐张说明其用途类别为包装设计图或形态参考图，视角标记为可选，并可补充其他用途或重要性说明。类别缺失时须请求补充，不执行生成。
- **FR-004**: 系统必须区分包装设计的品牌标识、文字、图案、颜色及版式与形态资料的形状、材质及结构职责。
- **FR-005**: 系统必须能处理包装不同区域的设计参考，不默认所有设计图展示同一平面；发现明显版本冲突时报告并询问运营人员确定有效版本，未经业务确认不得混用不同版本。
- **FR-006**: 系统必须能够综合形态参考的互补视角信息，包括可见的形状、厚度、封口、边缘、材质、褶皱与空间比例，不假定各图视角、完整度或可信度一致。
- **FR-007**: 系统必须识别或报告明显的参考资料冲突及无法确定的关键结构信息，不得假定单张形态图完整表达三维结构。
- **FR-008**: 未经业务确认，系统不得将缺失的包装结构信息描述为已真实还原。
- **FR-009**: 系统不得将形态参考图中的竞品商标、品牌名称、文字或图案直接作为目标商品品牌视觉内容。
- **FR-010**: 首版最终交付一张包装 Mock 组合图，由一次正常绘图任务生成并包含 F/L/R/B/T/Q 六种固定视图：正视、左侧、右侧、后视、俯视、右上 45° 正交；Q 平行线保持平行。生成与人工最终接受分别判断，技术重试及人工修订遵循 FR-012、FR-013。
- **FR-011**: 系统返回包装 Mock 组合候选图及供审核的信息；最终审核及结果记录由外部业务流程负责。人工接受图片时，品牌标识、包装文字及已确认的关键结构必须正确；其他视觉差异由业务人员裁量。
- **FR-012**: 生成前必须核对本次任务的业务授权及费用或其他副作用授权；核对范围包括任务、实际提示词、参考资料、模型、端点和已授权尝试。具备技术访问权限不等于获得任务授权；模型自述、布尔值或 API Key 不构成授权证据。
- **FR-013**: 首版不强制设置费用或耗时硬上限；系统须在执行前提供可获得的费用与耗时信息，由运营人员决定是否继续。技术故障允许有限自动重试：每个逻辑生成操作内，每个模型与接口组合最多 3 次（含首次）；当前批准的两个绘图模型均使用同一接口，因此每逻辑操作总计最多 6 次（含首次），仅在安全条件及授权覆盖时可达上限；重启或更换 attempt ID 不重置计数。当前接口的默认模型失败后切换备选模型；绘图的两个模型均失败后停止并报告，不切换至 Chat Completions 或 Gemini Official Format。仅对可确认安全的故障及授权覆盖的尝试执行；429、5xx 或网络超时本身不证明远程操作未执行。不得绕过权限拒绝或将质量不满意当作技术故障。质量不满意时，只有运营人员明确请求修订并取得适用授权后才可再次生成；人工修订不设轮数上限，每轮修订为关联历史的新操作，其技术重试独立计数。结果不明但可查询时，优先查询原任务状态，不重新提交或切换；无法查询时停止自动执行并保留结果不明状态，向调用方说明原任务可能仍在执行及可能产生重复费用或重复产物的风险。不得未经运营人员新的明确授权重新提交；运营人员了解风险并明确授权后可发起新尝试，该尝试必须与原任务可追溯关联，且不得覆盖原任务真实状态。
- **FR-014**: 系统必须校验每类图片的数量及有效性，数量不在首版范围时指出对应类别并停止生成。首版接受有效 JPEG、PNG 图片，其他格式须指出不支持并停止生成。首版不设固定业务文件大小上限；10 MiB 仅为候选值。系统仍须实施与业务上限分开的技术资源保护，校验实际图片内容和路径，防止异常解码资源消耗，并在资源不足时安全停止并报告；具体措施和供应商限制须验证。后续如声明单图大小限制，超限时必须在收费生成前拒绝并指出违规图片；上游报错后另以补丁升级方式更新限制。上游或运行环境的实际约束仍可能影响请求。
- **FR-015**: 形态资料存在明显结构冲突时，系统必须暂停并请求运营人员澄清；运营人员明确接受不确定性后，允许标明不确定性后继续生成预览。
- **FR-016**: 为控制成本或耗时，系统可以建议使用部分参考图，但必须先经运营人员确认所选集合，才能按该集合执行；不得预设自动筛选算法。mock 阶段不上传原始形态参考图是 FR-022 的既定阶段输入规则，不属于临时筛选建议；若进一步建议减少包装设计图，仍须确认。
- **FR-017**: 生成结果应以已确认的包装设计资料为目标品牌视觉的主要依据，尽可能正确呈现 Logo、包装文字、核心图案、颜色和版式；不得以竞品品牌内容代替目标商品设计。最终接受标准遵循 FR-011。
- **FR-018**: 系统建立并提供任务、形态组合版本、包装 Mock 组合版本、尝试和产物之间可核对的关联；修订保留历史产物，不得将历史产物作为当前结果。
- **FR-019**: 系统必须区分并报告生成成功、明确失败及结果不明；结果不明不得自动标记为失败或取消，也不得报告为成功。可查询时按 FR-013 优先查询原任务状态，无法查询时保留结果不明并遵循其恢复规则。
- **FR-020**: 包装设计 mock 之前，系统须在一次绘图模型调用的提示词中要求生成一张形态组合候选图；形态生成及修订阶段只输入一至六张产品形态参考图，不输入包装设计图或其他图片；修订意见通过文本传递，保留先前版本以供审核及追溯。该图同时包含六个固定视图，每个视图左上角分别标识 F=正视、L=左侧视、R=右侧视、B=后视、T=俯视、Q=右上 45° 正交。形态阶段的目标产物是一个包含六视图的图片文件，不是六个分别生成或交付的文件。绘图模型负责画面及字母标识，Host Agent 负责构造绘图提示词，Server 接收实际提示词并记录版本、摘要及任务绑定，无须额外合成。不能仅由模型自行判断并宣称形态或标识已完整验证；技术故障恢复仍遵循 FR-013，结果不明不得盲目重提。
- **FR-021**: 系统必须允许运营人员对形态候选图多轮提出修订并审核，记录各版本和确认状态；只有运营人员明确确认某一形态候选版本后，才能开始包装 mock。每轮收费操作遵循 FR-012、FR-013 的授权及未知结果恢复规则。
- **FR-022**: 包装 mock 必须关联并直接使用运营人员明确接受且无需再修订的六视图形态组合图原文件作为形态参考，不将该图拆分为六张；单次绘图只上传该组合图一张及一至两张包装设计图，最多三张，不上传原始形态参考图。保留任务、形态修订和包装候选产物间的可追溯关系，不得将未确认版本当作已确认版本。
- **FR-023**: 系统在包装 Mock 组合图生成后等待运营人员审核并确认具体版本；未经审核不得标记批准。运营人员不满意时可明确请求多轮修订，每轮生成新的关联产物并保留历史；收费及恢复遵循 FR-012、FR-013。

### Key Entities *(include if feature involves data)*

- **包装设计参考集合**: 一张或多张图片及其可用的区域、版本和用途说明，提供目标品牌视觉。
- **产品形态参考集合**: 一张或多张图片及其可用的视角、用途和可信度说明，提供包装空间形态与材质线索。
- **生成任务**: 可区分的任务及其两类参考集合、运营要求、业务授权、执行状态、限制及不确定性。
- **形态候选版本**: 一张供人工多轮修订、确认的中间图，关联任务与确认状态。
- **包装 Mock 组合版本**: 一张包含 F/L/R/B/T/Q 六个视图的包装 Mock 图片，关联任务、已确认形态版本、Attempt、产物和审核状态；历史修订保留。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 有效验收案例中，每个成功的正常阶段任务各返回一张包含六视图的组合图；形态候选须人工确认后才可生成包装 Mock，Mock 未审核不得标记批准。缺少任一固定视图不得报告完整，模型输出由人工审核；有效请求不保证成功。
- **SC-002**: 任一类别为空或无有效图片的验收案例中，100% 被指出受影响类别且不执行生成。
- **SC-003**: 对已识别或由运营人员指出的包装版本冲突，系统报告冲突、询问有效版本，未经业务确认不混用不同版本；视觉识别效果由代表性案例和人工审查评估，不承诺识别所有冲突。
- **SC-004**: 对已知单视角未覆盖的关键结构，验收检查不得出现未经业务确认即声称已真实还原的表述；未被识别的信息缺口由人工审核评估。
- **SC-005**: 每个包装 Mock 组合版本提供所属任务、已确认形态版本、Attempt、产物及供审核的信息，能与历史版本区分。
- **SC-006**: 在数量边界验收案例中，包装设计图 1、2 张及形态图 1、6 张满足数量条件；包装设计图 0、3 张或形态图 0、7 张均被拒绝并指出对应类别。
- **SC-007**: 100% 的未逐张声明用途类别案例在生成前要求补充；100% 的部分资料选择建议须经运营人员确认后才按建议执行。
- **SC-008**: 在有效 JPEG、PNG 及不支持格式的验收案例中，100% 的不支持格式被指出且不执行生成；有效格式仍须满足其余输入条件。
- **SC-009**: 外部业务流程负责包装 Mock 组合图最终审核及结果记录；MCP Server 将候选图及审核信息交付该流程。
- **SC-010**: 人工审核时，接受的图片必须满足已确认品牌标识、包装文字及关键结构正确；其他视觉差异由业务人员最终裁量。
- **SC-011**: 验收案例分别覆盖成功、明确失败、结果不明但可查询及结果不明且无法查询；状态与实际已知结果一致，无法查询时停止自动执行、保留结果不明并报告风险，新授权尝试须关联原任务且不覆盖其真实状态。
- **SC-012**: 如后续声明文件大小限制，对超过该限制的验收图片，收费生成前拒绝请求并指出违规图片；首版未声明时该验收项不适用。
- **SC-013**: 包装 mock 输入验收分别覆盖一张及两张包装设计图：请求仅包含对应设计图与一张已接受的六视图组合原图，总数分别为两张及三张；不发送原始形态参考图，未确认形态不得提交 mock。
- **SC-014**: 形态生成与人工修订的图片输入验收覆盖一张及六张形态参考图、零张及七张越界案例；一至六张时仅发送形态参考图，不发送包装设计图或其他图片，越界时拒绝生成并指出类别。

## Assumptions

- 运营人员有权提供和使用参考资料，并提供目标商品的包装设计；实际权限和业务授权需分别核实。
- 依赖可用的图像生成能力；Host Agent 构造提示词，Server 不调用独立 LLM。业务文件大小不设固定上限；技术资源保护和供应商限制待验证。
- 不包含 3D 建模、CAD、网格生成、自动裁切或六张独立视图输出；不预设自动筛选方案。
- 仓库中未发现已有功能规格，此前没有可核验的质量、成本、耗时及重试具体阈值；本轮明确审核底线、预算和重试原则，不编造数值。
