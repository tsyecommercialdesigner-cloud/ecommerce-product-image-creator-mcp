# 架构审查决策（草案，未实现）

审查范围为同机、本地文件输入、单用户 MVP；单进程 Python MCP Server、SQLite 和受限本地文件存储。本文不改变业务规格，不增加 LangGraph、Redis、Celery、PostgreSQL 或分布式服务。下列路径和确认组件是候选设计而非已运行能力。

## 授权来源比较（FR-005、007、012、013、015、016）

| 方案 | 信任边界和必要前提 | 风险与复杂度 |
|---|---|---|
| A 独立可信业务系统签发 | 已认证的业务主体独立审核明确的任务快照，签发可验证、过期、一次性且绑定任务的授权；服务端持久化并验证签名/来源。 | 可集中撤销和审计，但引入外部依赖、密钥管理及系统集成，当前本地 MVP 没有此系统，复杂度高。 |
| B 本地可信用户确认组件 | 同机运营人员通过独立于 Agent 可伪造输入的受保护交互确认完整快照；Server 独立验证可信来源、范围、有效期和一次性消费。 | 适合单机但同一 Windows 用户下 Agent 可能启动程序、写同权限文件或伪造输入；普通终端输入、权限相同的 JSON/SQLite 标志、普通弹窗、共享密钥或 Agent 调用确认工具都不足以证明本人。需要实际 OS 身份、受保护交互与进程间凭据/ACL 隔离的证据，复杂度中，方案目前未验证。 |
| C 可验证的 MCP Host 机制 | 只有 Host 能提供可验证的用户身份、确切任务摘要、费用范围和可供 Server 验证的授权证据，且支持防重放时可采用。 | 普通工具调用确认、文本与工具注解不自动构成业务授权；尚无证据证明本项目的 Codex 或 Claude Code 支持以上机制，复杂度取决于具体 Host。 |

**推荐 B 作为待验证的最小方向**：复用本机安全机制和受保护交互，优先同一安装包内的最小辅助组件，不默认增加后台服务。新增组件对应 FR-012/013，必要性是以不受 Agent 伪造的方式取得收费授权；较简单的对话确认或共享同用户文件无法验证来源。代价是打包、可信显示、防伪、系统权限和 Host 集成复杂性。需要明确系统威胁模型、用户身份、可验证通道、访问控制、组件真实性和失败行为；如同权限 Agent 能绕过，B 不成立，应退回 A、经证实的 C 或拒绝收费。普通用户无需理解签名实现，但必须能看到并确认实际输入、模型、端点、分组和可得费用/风险。

## 三工具的确认闭环

比较：三个工具加可信本地确认组件，保持模型可调用面小；新增 `confirm_product_image` 只便利数据录入，不能由模型调用即视为运营人员同意，仍须可信外部确认，增加状态和误用面。首版推荐保留三工具，可信组件处理全部需要用户确认的项目，非 MCP 的可信路径和实现待验证。

1. `prepare_product_image` 校验图片、冻结内容并生成 `task_id`、`revision`、规范化 `input_digest`，返回待确认项；不发收费请求。输入摘要覆盖实际图片内容摘要和顺序、类别、区域、版本、自然语言、选择子集、模型、端点、分组、输出设置与适用不确定性，不只是文件路径。具有效力的版本确认、结构不确定性接受和子集确认由可信组件记录；普通模型文字仅作未确认建议。
2. 确认组件向运营人员显示任务快照及其待确认项：包装有效版本、结构不确定性（含预览性质）、子集及其遗漏、可获得的费用和耗时、具体模型/端点/组别。普通业务选择和收费执行授权分别记录、分别标注作用；选择本身不授予费用操作。发生未知结果后需显示原任务仍可能执行及重复费用/产物风险，获得新的单次授权并关联原尝试。
3. 信任机制须确保确认来自实际被授权运营人员、非 Agent 可伪造，并绑定 `task_id/revision/input_digest`、操作范围、签发来源、有效期限及一次性标识。实现前须选定并验证此机制；未验证时 `submit_product_image` 拒绝收费提交。Server 校验确认内容、来源与可用性并在 SQLite 事务中原子消费收费授权，**同一授权竞争时最多一个请求获得提交资格**。
4. 图片、顺序、版本、已选集合、用户指令、模型、端点、分组、输出设置或已确认的不确定性变化时建立新 revision、重算摘要并使旧业务确认及授权无效；过期、撤销或消费的凭证不再可用。读取快照与提交必须一致，不能仅凭路径复用授权。
5. `get_product_image_task` 查询归属当前任务和尝试的本地状态；取得支持查询的上游 ID 时有界只读查询原尝试，不重新 POST。未知且不可查询时停止并告知风险，不将原尝试变成失败或取消。

## 三个状态维度与恢复（FR-010、011、013、018、019）

| 维度 | 值及含义 | 证据规则 |
|---|---|---|
| 本地任务 | `draft / awaiting_confirmation / ready / active / closed`；`closed` 只指本地流程结束，不能代表远端失败 | 本地持久记录；是否可提交由有效确认和授权另行决定。 |
| 上游尝试 | `not_submitted / submission_uncertain / accepted / running / succeeded / failed / unknown` | 提交前持久化 `submission_uncertain` 后才发送；仅可靠上游证据可记 accepted/running/succeeded/failed；无证据不得推断；unknown 不映射失败或取消。 |
| 本地交付 | `not_available / pending / delivered / download_failed / save_failed / missing_or_corrupt` | 上游成功不等于 delivered；只有唯一图片保存、摘要及关联登记后且读取校验通过才标 delivered。 |

提交前原子消费授权与意图只能约束本地并发，不能与远端收费提交组成事务，不承诺 exactly-once 或零重复费用。崩溃后 `submission_uncertain` 及未完成尝试按已有 ID 查询原任务；无 ID 或不可查询则保持 unknown，报告可能仍在执行及重复费用/产物风险。上游失败明确报告，禁止自动重试；上游成功下载/保存失败分别保留上游 succeeded 和本地错误，允许在授权访问及适用 URL 条件下恢复**下载**已有结果，不发起新生成。

图片先在产物根内独立临时文件保存并验证 MIME、字节、大小及摘要，再原子命名并提交 SQLite 关联；文件系统与 SQLite 之间没有跨系统原子事务。崩溃恢复时：

- 文件存在但数据库未登记：只依据持久化 attempt ID、受控文件名、摘要及上游成功证据核对；证据完备且唯一时可登记，否则隔离并报告人工处理，不能猜测归属或覆盖其他文件。
- 数据库记录 delivered 但文件缺失、不可读或摘要不符：将**交付状态**置为 missing_or_corrupt 并报告，保持上游 succeeded；允许安全重取原结果，绝不自动重生成。
- 下载失败或本地写入/重命名失败：分别报告 download_failed 或 save_failed；不得以任务失败覆盖上游成功。重启扫描只限本项目受控目录，不删除未知文件或用户数据。

## 本地文件安全（FR-001–004、014、018）

输入根与产物根分开，受启动账号和 ACL 限制；路径规范化并处理链接/重解析点和并发替换，打开后校验实际 JPEG/PNG、每类数量、单图/总字节、像素与解码内存上限。单图 10 MiB 仅为讨论候选；各限制按模型、端点、分组、服务和传输能力确认并取得必要业务批准，未确定前不得宣称可生产。对快照文件逐项内容摘要及排序绑定授权，提交前从不可变受保护快照读取并复验；变更则失效并重新确认。仅向经授权的目标发送数据；返回 URL 下载须遵循 [供应商适配契约](provider-adapters.md) 网络安全限制。替身和崩溃注入测试不能证明同机恶意进程不能伪造身份。
